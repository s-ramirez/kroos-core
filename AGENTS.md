# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## Build and Test

```sh
go build ./...              # Build all packages
go test ./...               # Run full test suite
go test ./internal/tools/   # Run tests for a single package
go test ./internal/tools/ -run TestGrepToolFindsPattern  # Run a single test
go test -v ./...            # Verbose output
```

Run the CLI: `go run ./cmd/kroos` (defaults to the OpenAI API).

Bootstrap an instance: `go run ./cmd/kroos init` scaffolds `$KROOS_HOME` (templates from `cmd/kroos/templates/`, kept if present) then runs an interactive, idempotent setup wizard (`cmd/kroos/init.go`): numbered menus for Providers (ChatGPT login + model picked from the live catalog, oMLX URL/key + connection test + model, default provider, fallback), Channels (Discord/Telegram/iMessage enable/disable + fields), Heartbeat and Extras. It starts from `$KROOS_HOME/config.json`, Enter keeps a value, `-` clears it, secrets are masked and read without echo on a TTY, and each change is saved immediately to `config.json`. Re-runnable any time.

Environment variables: `KROOS_PROVIDER` (`chatgpt` default | `omlx`), `KROOS_OMLX_URL` (no default), `KROOS_OMLX_API_KEY`, `KROOS_MODEL` (model for the selected provider; default `KROOS_CHATGPT_MODEL` / `KROOS_OMLX_MODEL`, each empty = first model the provider lists), `KROOS_FALLBACK` (default `true`), `KROOS_LLM_TIMEOUT` (default `5m`), `KROOS_SUBAGENT_LLM_TIMEOUT` (default: same as `KROOS_LLM_TIMEOUT`), `KROOS_ATTACHMENT_DIR` (where channels save inbound media; default `$TMPDIR/kroos-attachments`, one subdir per channel), `KROOS_IMAGE_INPUT` (default `true`; inline image attachments as vision input — set `false` for non-vision models).

Heartbeat environment variables (all optional; heartbeat is disabled unless `KROOS_HEARTBEAT_INTERVAL` is set):
`KROOS_HEARTBEAT_INTERVAL` (Go duration, e.g. `15m`), `KROOS_HEARTBEAT_TARGET` (default `cli`; `cli` | `imessage` | `discord` | `none`), `KROOS_HEARTBEAT_TO` (recipient handle/channel ID for non-CLI targets), `KROOS_HEARTBEAT_MODEL` (model override for heartbeat turns; empty = same as default), `KROOS_HEARTBEAT_PROMPT` (custom prompt text), `KROOS_HEARTBEAT_ACTIVE_HOURS_START` / `KROOS_HEARTBEAT_ACTIVE_HOURS_END` (`HH:MM` 24h window; both must be set), `KROOS_HEARTBEAT_TIMEZONE` (IANA name; empty = local). Each tick runs as an isolated background task; replying `NOTHING_TO_REPORT` (or legacy `HEARTBEAT_OK`) suppresses delivery.

iMessage channel environment variables (all optional; channel is disabled unless both URL and password are set):
`BLUEBUBBLES_ENABLED` (default `true`; set to `false`/`0` to force-disable even when creds are present), `BLUEBUBBLES_SERVER_URL`, `BLUEBUBBLES_PASSWORD`, `BLUEBUBBLES_WEBHOOK_HOST` (default `127.0.0.1`; use `0.0.0.0` if BlueBubbles runs on another machine), `BLUEBUBBLES_WEBHOOK_PORT` (default `8421`), `BLUEBUBBLES_WEBHOOK_PATH` (default `/bluebubbles`), `BLUEBUBBLES_WEBHOOK_URL` (URL BlueBubbles should call; default derived from host/port/path), `BLUEBUBBLES_REGISTER_WEBHOOK` (default `true`), `BLUEBUBBLES_ALLOWED_USERS` (comma-separated), `BLUEBUBBLES_GROUP_TAG` (e.g. `@kroos`), `BLUEBUBBLES_READ_RECEIPTS` (default `true`; read receipts + typing indicator, needs BlueBubbles private API).

Discord channel environment variables (channel is disabled unless `DISCORD_BOT_TOKEN` is set):
`DISCORD_ENABLED` (default `true`; set to `false`/`0` to force-disable even when a token is present), `DISCORD_BOT_TOKEN` (bot token), `DISCORD_ALLOWED_USERS` (comma-separated Discord user snowflakes), `DISCORD_GUILD_TAG` (e.g. `@kroos` — required in guild channels unless the bot is @mentioned; DMs bypass the check).

## Architecture

**Instance home** (`config.Home()`): all per-instance state lives in `$KROOS_HOME` (default `~/.kroos`; read from the real env only, exported to the process so bash sees it): `config.json`, `.env`, `auth.json`, `AGENTS.md`/`IDENTITY.md`/`USER.md`, `skills/`, `subagents/`, `profiles/`, `memory/`, `state/` (conversations), `workspaces/`, `schedule/`, `tasks/`, `logs/`. Nothing instance-specific is read from or written to the cwd or the code checkout; cwd is only the tools' working directory (deploy runs in `$KROOS_HOME/workspace`). No personal defaults in code (e.g. `omlx.url` is empty until set).

**Agent loop** (`internal/cli/runner.go`): The core cycle is `Runner.agentLoop()`. It calls the LLM, dispatches any tool calls through the `Registry`, appends results as `"tool"` role messages, and loops until the model responds with text. If the model returns empty content after tool calls, the runner retries up to 2 times with a follow-up nudge message.

**Tool interface** (`internal/tools/types.go`): Every tool implements `Tool` — `Definition()` returns metadata and JSON schema, `Execute(ctx, json.RawMessage)` returns `(ToolResult, error)`. Tool-level errors (bad args, file not found) are returned as `ToolResult{IsError: true}` via the `errorResult`/`errorResultf` helpers, not as Go errors.

**Tool hooks** (`internal/tools/types.go`): `ToolHook` interface with `BeforeToolCall` (can block execution by returning a reason string) and `AfterToolCall`. Hooks are registered on the `Registry` and invoked by the runner around each tool execution.

**Filesystem abstraction** (`internal/tools/fs.go`): Tools that touch files (read, write, edit, ls) take an `FS` interface. Production uses `OSFS{}`. Tools that walk directories (grep, find, bash) use `os` directly.

**Skills** (`internal/skills/`): Skills are markdown files (`SKILL.md`) with YAML frontmatter that provide specialized instructions to the LLM. `LoadSkills(dirs...)` scans directories for `SKILL.md` files, parses frontmatter (name, description, disable-model-invocation), and returns validated `Skill` structs. Skills are discovered from `$KROOS_HOME/skills/`. Users invoke skills with `/skill:<name> [args]`, which the runner expands to the skill file content before sending to the LLM. Skills with `disable-model-invocation: true` are excluded from the system prompt but remain invocable via `/skill:`.

**System prompt** (`internal/prompt/system.go`): `BuildSystemPrompt(tools, skills, env)` assembles the prompt from sections: environment info (OS, arch, workspace, time), per-tool guidelines, conditional tool-selection rules, and an `<available_skills>` XML block listing visible skills with their name, description, and file location.

**Providers** (`internal/llm/provider.go`): only `chatgpt` and `omlx`. `llm.Providers.New(provider, model, timeout)` builds clients; agent/subagent/profile frontmatter `provider:` picks one (empty = main agent's). `chatgpt` = ChatGPT subscription via Codex OAuth (ported from hermes-agent `auth_codex.py`): `kroos login`/`kroos logout` run the device-code flow against auth.openai.com, tokens in `$KROOS_HOME/auth.json` (0600), auto-refresh near JWT expiry and on 401; `ChatGPTClient` (`chatgpt.go`) adapts chat-completions messages to the Responses API at `chatgpt.com/backend-api/codex/responses` (SSE, `store:false`, `ChatGPT-Account-ID` from JWT). `omlx` = chat-completions `Client` at `omlx.url` with `omlx.api_key`. Providers are interchangeable: each has a default model (`chatgpt.model`/`omlx.model`, empty = first model the provider lists — ChatGPT's catalog depends on the plan, so no model is hard-coded; `model` overrides for the selected provider). `Providers.Client()` returns a `FallbackClient` (`fallback.go`) that tries the requested provider then the others on their default models (`fallback`, default true), skipping a failed provider for 1 min, or 10 min when it rejected the request with a 4xx other than 408/429 (cooldown shared across clients). At startup an unready provider (no login / no URL) is swapped for the first ready one with a warning, never fatal. `kroos models [provider]` lists models (ChatGPT: `GET backend-api/codex/models?client_version=…`, visible slugs by priority; oMLX: `GET /v1/models`); `kroos models select [--project] [pick]` saves `provider`+`model` to config (`cmd/kroos/models.go`). In-session `/model` (dispatcher `SlashCommands`) lists/sets a per-conversation override (`Conversation.Provider/Model`, persisted with history, kept across `/new`); `/model default` clears; the runner builds the override client via `Runner.ClientFor`. Picks: list number, model name, or `provider:model`.

**LLM client** (`internal/llm/client.go`): `ChatClient` interface with a single `Chat()` method. The concrete `Client` posts to `/v1/chat/completions` (OpenAI-compatible format). The runner accepts a `ClientForModel func(model string) ChatClient` factory for per-turn model overrides (used by heartbeat).

**Heartbeat system** (`internal/heartbeat/`): `heartbeat.Register` injects a synthetic `mode=task` job (ID `heartbeat`) into the scheduler with `Deliver` from target/to, `Model`, and `ActiveHours`. Each tick runs through `tasks.Executor` like any background task (isolated context, delivery, token suppression, dedup, history). `schedule.Job.ActiveHours` is generic: `sched.Channel` drops any event fired outside its window.

**Self-healing** (`internal/health/`, `internal/cli/doctor.go`, `cmd/kroos/doctor.go`, `internal/tools/doctor_tools.go`): `health.Monitor` counts consecutive failures per component (`channel:<name>` from the dispatcher supervisor, `provider:<name>` via `Providers.OnResult`); 3 opens an incident (persisted to `$KROOS_HOME/state/health.json`), success/1 min uptime resolves it. On a new incident kroos posts an alert to the first healthy channel's home thread (else CLI) asking the user to reply `/doctor`. `/doctor [note]` (dispatcher `SlashCommands`) submits a `doctor` task that reports back to that conversation. The doctor gets read/write/edit/bash/grep/ls/find/web tools plus `kroos_config` (list/get/set/unset non-secret keys; secrets masked, never settable) and `kroos_health` (status, restart a component's listener now, `restart_process` = exit after the report so launchd restarts; service only via `KROOS_SERVICE=1`). Code bugs: fix in a git worktree under `$KROOS_HOME/workspace/doctor/` on a `doctor/<slug>` branch, test, push, `gh pr create`. `doctorGuard` hook blocks git mutations in the live checkout (`KROOS_SOURCE_DIR`, default checkout containing the binary), pushes to anything but `doctor/*`, force-push, `gh pr merge`, and writes to `auth.json`/`.env`. The deploy plist sets `KROOS_SERVICE`, `KROOS_SOURCE_DIR`, `KROOS_LOG_FILE`.

**Channel interface** (`internal/channel/channel.go`): `Channel` has `Name() string`, `Listen(ctx, out chan<- Inbound) error`, and `Send(ctx, Outbound) error`. The `Dispatcher` fans out to all registered channels, routes each inbound message to a conversation keyed by `(Channel, Thread)`, and calls back `Send` on the originating channel with the reply. Channels are isolated: only a `channel.Terminal` channel (the CLI; Ctrl-D) ending stops the dispatcher; any other channel whose `Listen` errors (bad token, unreachable server) is logged and restarted with exponential backoff (1s→5m, reset after 1 min up) while the rest keep running.

**Attachments** (`internal/channel/attachment.go`): Channel-agnostic media plumbing. Channels download inbound media with `channel.FetchAttachment`/`SaveAttachment` (25 MB cap, safe filenames, MIME sniffing) into `channel.AttachmentDir(name)` and set `Inbound.Attachments`; `Inbound.MessageID` becomes `Outbound.ReplyTo` so channels can thread replies (groups only). The dispatcher copies attachments onto `Conversation.Attachments` for the turn; the runner (`internal/cli/attachments.go`) lists each by path and, when `ImageInput` is set, inlines png/jpeg/gif/webp ≤5 MB as base64 `image_url` parts. The runner puts the conversation `Key` on the context (`channel.WithKey`) so the `send_file` tool (`internal/tools/send_file.go`) can send a local file to the current chat as `Outbound.Attachments`; each messaging channel's `Send` uploads attachments before text. `channel.DropMetaLines` is shared by all channels.

**iMessage channel** (`internal/channel/imessage/`): BlueBubbles only. On `Listen` it binds the webhook server, pings `/api/v1/ping`, reads `/api/v1/server/info` (private API + helper → enables typing/read receipts), and registers its webhook URL (password in query) via `/api/v1/webhook`, unregistering on shutdown. Only `new-message` events are handled; tapbacks are dropped; message GUIDs are deduped. Only forwards messages from `OwnerHandles`; group chats (`;+;` in chatGuid) additionally require `GroupTag`. Inbound attachments are downloaded into `Inbound.Attachments`. Outbound attachments upload via `/api/v1/message/attachment`; in group chats the first bubble is threaded under `Outbound.ReplyTo` when the private API is on. Outbound text has Markdown stripped (`stripMarkdown`) and meta-lines like `[tokens: ...]` filtered (`dropMetaLines`), then is sent one bubble per paragraph (split past 4000 chars). The REST client (`api.go`) URL-encodes the password and keeps it out of errors; logs redact phone numbers/emails. Handle normalization (`normalizeHandle`) strips service prefixes and normalises phone formatting. The `imessage_send` tool (`internal/tools/imessage_send.go`) reuses the exported `imessage.Client`: phone/email recipients resolve to an existing chat by `chatIdentifier` (never by participant, to avoid leaking DMs into groups), else a new chat is created via `/api/v1/chat/new`.

**Discord channel** (`internal/channel/discord/`): Uses `github.com/bwmarrin/discordgo` to receive messages via the Discord gateway (websocket) and send via REST. Only forwards messages from `OwnerIDs`; guild channels additionally require either an @mention of the bot or the literal `GuildTag` in the message body, which is stripped before dispatch. DMs bypass the tag check. The `Thread` is the Discord channel ID. Outbound meta-lines (`[tokens: ...]`) are filtered and messages over 2000 chars are chunked. Attachments are downloaded from the CDN on receive and uploaded via `ChannelMessageSendComplex`; replies in guild channels reference the triggering message. The `discord_send` tool (`internal/tools/discord_send.go`) lets the agent proactively post to any channel or DM a user (it opens a DM channel automatically via `UserChannelCreate` when `kind=user`).

## Conventions

- **Minimal external dependencies.** Prefer the standard library. External dependencies are allowed when they earn their keep — pick focused, small, well-maintained packages over reimplementing non-trivial logic. Avoid dependencies that pull large transitive trees, force CGo on the build, or reimplement something the stdlib already does well.
- **Tool parameter structs** are named `<ToolName>Params` with JSON tags matching the schema field names exactly. Unmarshal with `json.Unmarshal(raw, &params)`.
- **Tool definitions** are module-level vars (`var bashDefinition = ToolDefinition{...}`), not generated at runtime.
- **Directory skipping**: grep and find skip `.git`, `node_modules`, `__pycache__`, `.cache` via `filepath.SkipDir`.
- **Output truncation**: Tools enforce default limits (read: 2000 lines, grep: 100 matches, ls: 500 entries, find: 1000 results) and append a `[... limit reached]` marker when truncated.
- **Skill files** are `SKILL.md` with YAML frontmatter (`name`, `description`, `disable-model-invocation`). Name must be lowercase alphanumeric with hyphens, max 64 chars. Description is required.
- **Tests** use `t.TempDir()` for filesystem tests, `httptest.NewServer` for HTTP tests, and `json.Marshal(Params{...})` to build tool input. A shared `writeFile` helper exists in `grep_test.go` and `loader_test.go` for creating temp files.
